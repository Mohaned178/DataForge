# ADR-0015: Hardening and scale: measure first, version the events, check the environment

Status: Accepted (Milestone 10).

## Context

Nine milestones built the product: engine, chaos planner, validation, Kafka, windows, persistence, API and UI.
Milestone 10 asks whether it holds at the scenario limits (100,000 orders), and closes the gaps the earlier
milestones deferred to it: streaming "if profiling calls for it", event schema versioning, a reproducible
Compose environment, documentation. The specification forbids premature optimization and worker threads before
profiling proves them (sections 5 and 10), so the order is: measure, then decide.

## Decisions

1. **Profile with a repeatable command, not a one-off.** `pnpm profile` (`scripts/profile/`) runs the CLI stages
   as child processes (peak memory from each process's own resource usage) and, with `--api`, the API stages
   (run, downloads, an execution) while probing `/health` for event-loop stalls. The numbers are in
   [docs/performance.md](../performance.md). The script lives outside `packages/`, so the determinism guard
   does not apply to it and nothing in the engine knows about it.
2. **No streaming generation or serialization.** At the limit every CLI stage peaks under 2 GB and finishes in
   9 to 14 seconds (455,251 events, 139 MB log). Streaming would change the shape of `simulate()` (a pure
   function returning the whole result that the golden tests, the CLI and the API all share) to save memory
   nobody is short of. The API download is the one candidate, and it must verify the entire file's checksum
   before sending a byte (ADR-0011), so streaming it means reading the database twice. Revisit when a target
   size beyond the limits is wanted.
3. **No worker threads yet; the evidence is recorded and the choice left to the product owner (D-10.1).** The
   API stalls for 9.4 s while generating a run at the limit and 28.4 s while running an execution (0.3 to 1.0 s
   at the specification's size). That is real, but it affects a single-user local tool at the largest size the
   schema accepts, and the fix is not free: either 130 MB documents cross a thread boundary by structured clone
   (itself a multi-second stall on the main thread) or a worker opens its own database connection and reads and
   writes by run id, which means the pipeline moves out of the request path. If the answer to D-10.1 is yes,
   that second design is the one to build, for executions first.
4. **Event schema versioning is upcasting at the three read boundaries.** `packages/core/src/events/upcast.ts`
   holds `EVENT_UPCASTERS`: one pure function per version step (the entry under `n` turns a version `n` record
   into `n + 1`), applied until the record reaches `EVENT_SCHEMA_VERSION`. It is used wherever stored events
   are read: the JSONL log (`parseEventLog`), a database row (`fromEventRow`) and a Kafka record (the
   delivery-record contract). Alternatives considered:
   - *Versioned Zod schemas, one per version, parsed as a union.* Every consumer of an event would then handle
     every version; upcasting keeps one current shape in the engine, the rules, the projection and the targets.
   - *Migrating stored data in place.* Run files carry checksums and are meant to be immutable; rewriting them
     would make an old run's checksum disagree with its manifest. Reading through an upcaster changes nothing
     on disk.

   The registry is empty today: version 1 is the only schema that has existed, and bumping the version to demo
   the mechanism would change every golden hash for no reason. The mechanism is tested with an injected
   registry (a pretend version 0 that named the event time differently) and with the default registry's
   refusals. A version **newer** than the engine reads is an error naming both versions ("schemaVersion 2 is
   newer than the version this engine reads (1); upgrade DataForge to read this event"), never a guess; an
   **older** version with no upcaster says which upcaster is missing. The first real schema change adds its
   upcaster, bumps `EVENT_SCHEMA_VERSION` and `ENGINE_VERSION` as usual, and the golden test will say so.

   What upcasting does not do: `dataforge verify` still compares a run's files to its manifest, so a run
   generated by an older engine is read correctly but is reported as generated by another engine version
   (the reproducibility check regenerates with the current one). That is the accurate answer.
5. **The Compose environment is checked by a test, not by a promise.**
   `apps/api/test/reproducible-environment.test.ts` fails when an image is not pinned to an exact version, a
   service has no health check (so `docker compose up --wait` would not mean ready), a `${VAR:-default}` in
   `compose.yaml` is missing from `.env.example` or differs from it, the documented connection settings
   disagree with the published ports and the database credentials, `.env.example` is a configuration the API
   refuses, or `.env.example` documents a variable no code reads. It runs in `pnpm check`, with no Docker.
6. **The demo is a script over the public API, not a fixture.** `pnpm demo:seed` registers the example
   scenarios and profiles, generates two runs and launches five executions through the same HTTP endpoints the
   UI uses, so what it leaves behind is exactly what a user would have made by hand, and it works against any
   running API. It is idempotent (same names, same runs, same executions are reused). Each execution has an
   expected verdict in the script; a different one is printed beside the result.
7. **Left out on purpose.** A clean-up command for execution work directories and Kafka topics (the roadmap's
   candidate): the directories are under the system temp directory and `docker compose down` removes the
   topics; a command that deletes data is worth a decision of its own. Serving the web UI from the API and
   production hosting (D-8.1): the API has no authentication and stays on 127.0.0.1, which is what makes a
   hosted instance out of scope under specification section 11.

## Consequences

- The numbers a user can ask about ("how big can it go?") have a source, a command and a date.
- A schema change is now a planned, tested operation instead of a flag day, and no existing byte changes.
- Compose and `.env.example` can no longer drift apart silently.
- The API's single-threaded event loop is a documented limitation with a measured size and a named design,
  waiting for the product owner's answer.
